Lo nuevo de hoy

Concepto

Interbloqueo: dos o más hilos esperan cada uno algo que tiene otro, y ninguno puede avanzar.

Palabra

synchronized (objeto) { … }: coge el cerrojo de ese objeto solo durante el bloque, en vez de en todo el método.

Método

getState() de la clase Thread: devuelve el estado del hilo. Un hilo que espera el cerrojo de un objeto está en BLOCKED.

Más adelante

Un cerrojo con tiempo máximo: ReentrantLock y tryLock() (solo en el último ejercicio).

Repaso: synchronized, sleep(), this, Runnable y throws funcionan igual que en 6.4, 6.5 y 6.6.

¿Qué ha salido?

Hilo 2 tiene B
Hilo 1 pide B
Hilo 2 pide A
Hilo 1: BLOCKED
Hilo 2: BLOCKED
▮ (el programa no termina)

  • En NetBeans, el botón de ejecución sigue activo: hay que detenerlo a mano

No hay ningún error. El programa simplemente se queda parado: eso es lo que hace tan difícil encontrarlo.

Vamos a pensarlo paso a paso

  1. ¿Quién tiene A? El hilo 1, y no lo suelta
  2. ¿Quién tiene B? El hilo 2, y no lo suelta
  3. ¿Qué pide el hilo 1? B, que tiene el hilo 2 → espera
  4. ¿Qué pide el hilo 2? A, que tiene el hilo 1 → espera
  5. ¿Quién puede soltar algo primero? Nadie. Los dos esperan al otro: un círculo

El círculo

Flechas verdes: lo tiene. Flechas rojas: lo espera. Se cruzan: hay un círculo, y nadie sale.

Los estados de un hilo

EstadoCuándo ocurre
NEWSe ha creado con new Thread(...), pero aún no se ha llamado a start()
RUNNABLEEstá en marcha (o listo para que le toque)
BLOCKEDEspera el cerrojo de un objeto synchronized
WAITINGEspera un aviso: wait() o join()
TIMED_WAITINGEspera un tiempo: sleep()
TERMINATEDHa acabado su run()

Con wait() sin notify() los hilos se quedan en WAITING. Con interbloqueo, en BLOCKED. Los dos «cuelgan», pero por motivos distintos.

Ahora sí: el código

Cada hilo es un Trabajo que necesita los dos ficheros a la vez.

    public void run() {
        String nombre = Thread.currentThread().getName();
        synchronized (primero) {
            System.out.println(nombre + " tiene " + primero.getNombre());
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
            }
            System.out.println(nombre + " pide " + segundo.getNombre());
            synchronized (segundo) {
                System.out.println(nombre + " tiene " + primero.getNombre() + " y " + segundo.getNombre() + ": trabaja");
            }
        }
        System.out.println(nombre + " termina");
    }
  • 1. Coge el cerrojo del primer fichero
  • 2. Lo dice y espera un segundo sin soltarlo (sleep() no suelta nada)
  • 3. Dice qué fichero va a pedir
  • 4. Pide el cerrojo del segundo, mientras sigue con el primero

Y quién pide qué

        Thread h1 = new Thread(new Trabajo(a, b), "Hilo 1");
        Thread h2 = new Thread(new Trabajo(b, a), "Hilo 2");
        h1.start();
        h2.start();
  • El hilo 1 recibe (a, b): primero A y después B
  • El hilo 2 recibe (b, a): primero B y después A
  • Son los mismos dos objetos para los dos hilos, y cada uno pide en orden contrario

Cuándo puede haber interbloqueo

Para que ocurra se tienen que cumplir las cuatro cosas a la vez:

  1. Exclusión mutua: el recurso solo lo usa un hilo cada vez (synchronized)
  2. Retener y esperar: un hilo se queda con un recurso mientras pide otro
  3. Sin quitárselo: nadie puede arrebatarle el recurso al hilo que lo tiene
  4. Espera en círculo: A espera a B y B espera a A

Si evitamos una sola, no hay interbloqueo. Hoy probamos cinco formas de hacerlo.

¿Cuál quitarías primero?

Mirad las cuatro condiciones y pensad por parejas (1 minuto).

  • Exclusión mutua: ¿podemos quitarla? No. Sin synchronized vuelve la condición de carrera de 6.3. Los ficheros tienen que ser de uno en uno
  • Espera en círculo: ¿cómo se deshace un círculo? Haciendo que no sea un círculo → soluciones 1, 2 y 4
  • Retener y esperar: ¿y si no se retiene nada? → solución 3
  • Sin quitárselo: ¿y si el hilo se rinde y suelta lo que tiene? → solución 5 (reto)

Solución 1 · Mismo orden

Pensad: si los dos hilos pidieran primero A y después B, ¿podría cada uno quedarse esperando al otro?

No. El que llega segundo espera A y no tiene nada cogido, así que no bloquea al otro. Cuando el primero acaba, entra.

Rompe la condición: espera en círculo

Solución 2 · Un solo cerrojo

Pensad: si en vez de un cerrojo por fichero hubiera uno solo para los dos, ¿podría un hilo quedarse con la mitad?

No. Quien tiene el cerrojo tiene los dos ficheros a la vez, y el otro espera a tenerlos todos. El orden en que se piden ya no importa.

Rompe la condición: espera en círculo

Solución 3 · No retener

Pensad: ¿qué pasaría si el hilo soltara el primer fichero antes de pedir el segundo?

Mientras espera, no tiene nada cogido: nadie espera por él y no se forma el círculo. Solo vale si el trabajo no necesita los dos ficheros a la vez.

Rompe la condición: retener y esperar

Solución 3 · Qué cambiar (6 min)

  3. Después, mostrad que pide el segundo fichero

Solución 4 · Orden por número

Pensad: la solución 1 depende de que todos pidan en el mismo orden. ¿Y si alguien se equivoca en Principal?

Vuelve el interbloqueo. Para que no pase, cada fichero lleva un número y Trabajo los ordena él mismo, de menor a mayor, le lleguen como le lleguen.

Rompe la condición: espera en círculo

Solución 5 · Tiempo máximo (reto)

Pensad: ¿puede el propio hilo rendirse si el segundo fichero no llega en un tiempo?

Sí: pide el segundo diciendo cuánto espera como mucho. Si no llega, suelta el primero, espera un rato al azar y lo reintenta.

Rompe la condición: sin quitárselo

Lo que necesitas: ReentrantLock

  • ReentrantLock: un cerrojo que se pide y se suelta a mano, sin synchronized
  • lock(): pide el cerrojo y espera hasta tenerlo
  • tryLock(1, TimeUnit.SECONDS): lo pide y espera como mucho 1 segundo. Devuelve true si lo consigue y false si no
  • unlock(): suelta el cerrojo. Hay que soltarlo siempre

Solución 5 · Qué cambiar (10 min)

  1. Copiad Interbloqueo con el nombre InterbloqueoTiempo
  2. En Fichero: un atributo ReentrantLock y un método que lo devuelve
  3. En Trabajo: un while hasta que hecho sea true, dentro de un try
  4. Primer fichero con lock(), sleep() de 1 s, y segundo con tryLock(1, TimeUnit.SECONDS) en un if
  5. Si da true: trabaja, unlock() de los dos y hecho = true
  6. Si da false: mensaje de reintento, unlock() del primero y sleep() al azar
  7. En Principal, main espera 8 segundos

Ejecutad: varias veces. Los dos terminan, y a veces hay algún reintento.

Pistas y ayudas: enunciado, ejercicio 6.

¿Cuál uso?

SoluciónCondición que rompeMejor cuando…
1 · Mismo ordenEspera en círculoControlas todo el código que pide los recursos
2 · Un solo cerrojoEspera en círculoLos recursos van siempre juntos y no importa esperar
3 · No retenerRetener y esperarEl trabajo no necesita los dos recursos a la vez
4 · Orden por númeroEspera en círculoMuchos recursos y mucha gente tocando el código
5 · Tiempo máximoSin quitárseloNo puedes asegurar el orden y puedes repetir el trabajo

En la práctica, lo más usado es la 1 y la 4: pedir siempre en el mismo orden.

Para decidir (por parejas, 2 minutos)

  1. Un banco pasa dinero de la cuenta X a la cuenta Y. A la vez, otro hilo pasa de Y a X. Hay que bloquear las dos cuentas a la vez. ¿Qué solución usas? La 4: ordenar las cuentas por su número, y bloquear siempre primero la de número más bajo
  2. Un hilo imprime un informe con dos ficheros, pero lee uno y después el otro, sin necesitarlos juntos. ¿Cuál? La 3: no retener, usar uno, soltarlo y pedir el otro
  3. Un programa pide un recurso externo que a veces tarda muchísimo, y repetir el trabajo no cuesta nada. ¿Cuál? La 5: tiempo máximo y reintento

Errores típicos

  • Pensar que sleep() suelta el cerrojo: no lo suelta, solo wait() lo hace
  • Que cada hilo pida los recursos en orden distinto
  • Creer que un programa parado es siempre un interbloqueo: también se queda parado si falta un notify()
  • Probarlo una vez, que salga bien, y darlo por bueno: el interbloqueo depende del momento
  • Quitar los synchronized para que no se bloquee: desaparece el bloqueo, pero vuelve la condición de carrera
  • Con ReentrantLock: olvidar el unlock() en algún camino. El cerrojo se queda cogido para siempre

    public Trabajo(Fichero uno, Fichero otro) {

Solución 5 · Tiempo máximo

Fichero: cada fichero guarda su propio ReentrantLock.

import java.util.concurrent.locks.ReentrantLock;

public class Fichero {

    private String nombre;
    private ReentrantLock cerrojo = new ReentrantLock();

    public Fichero(String nombre) {
        this.nombre = nombre;
    }

    public String getNombre() {
        return nombre;
    }

    public ReentrantLock getCerrojo() {
        return cerrojo;
    }
}
