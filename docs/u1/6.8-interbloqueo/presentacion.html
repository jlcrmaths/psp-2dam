Interbloqueo

PSP · 2º DAM · Apartado 6.8

Objetivo de la clase

  • Entender qué es un interbloqueo (en inglés, deadlock)
  • Ver cómo se produce en un ejemplo con dos hilos y dos ficheros
  • Reconocerlo: el programa no da error y no termina
  • Saber qué estados puede tener un hilo, y cuál es el de un hilo interbloqueado
  • Evitarlo: pedir los recursos siempre en el mismo orden

De «esperar un aviso» a «esperar al otro»

En 6.4 los hilos esperaban con wait() a que alguien les avisara. Si el aviso no llegaba, se quedaban colgados.

Hoy es distinto: cada hilo tiene algo que el otro necesita, y los dos esperan a que el otro lo suelte. Ninguno lo soltará.

Una idea para recordarlo

Dos personas en una puerta estrecha, una frente a la otra.

  • Cada una espera a que la otra se aparte para poder pasar
  • Ninguna se aparta primero, porque está esperando a la otra
  • Pueden quedarse así para siempre

Lo nuevo de hoy

Concepto

Interbloqueo: dos o más hilos esperan cada uno algo que tiene otro, y ninguno puede avanzar.

Idea

Un hilo puede tener el cerrojo de un objeto y pedir el de otro. Si dos hilos lo hacen en orden contrario, se bloquean.

Método

getState() de la clase Thread: devuelve el estado del hilo. Un hilo que espera el cerrojo de un objeto está en BLOCKED.

Palabra

synchronized (objeto) { … }: coge el cerrojo de ese objeto solo durante el bloque, en vez de en todo el método.

Repaso: synchronized, sleep(), this, Runnable y throws funcionan igual que en 6.4, 6.5 y 6.7.

Cuándo puede haber interbloqueo

Para que ocurra se tienen que cumplir las cuatro cosas a la vez:

  1. Exclusión mutua: el recurso solo lo usa un hilo cada vez (synchronized)
  2. Retener y esperar: un hilo se queda con un recurso mientras pide otro
  3. Sin quitárselo: nadie puede arrebatarle el recurso al hilo que lo tiene
  4. Espera en círculo: A espera a B y B espera a A

Si evitamos una sola, no hay interbloqueo.

El ejemplo: dos ficheros

  • Hay dos ficheros, FicheroA y FicheroB. Cada uno solo admite un hilo a la vez
  • El hilo 1 entra en A y después necesita B
  • El hilo 2 entra en B y después necesita A

Proyecto Interbloqueo

FicheroA: entra en A y pide B

public class FicheroA {

    public synchronized void metodoA(FicheroB b) {
        String nombre = Thread.currentThread().getName();
        System.out.println(nombre + " entra en fichero_A");

        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
        }

        System.out.println(nombre + " intentando acceder a fichero_B");
        b.metodoB(this);
    }
}

Línea por línea: FicheroA (1)

  • public synchronized void metodoA(FicheroB b)
    Para entrar, el hilo coge el cerrojo de este FicheroA. Recibe el FicheroB que va a pedir después
  • System.out.println(nombre + " entra en fichero_A");
    El hilo dice que ya ha entrado en A
  • Thread.sleep(1000);
    Espera un segundo. El sleep() no suelta el cerrojo: sigue teniendo A. Este segundo da tiempo a que el otro hilo entre en B

Línea por línea: FicheroA (2)

  • System.out.println(nombre + " intentando acceder a fichero_B");
    Va a pedir el otro fichero
  • b.metodoB(this);
    Llama al método de B, que también es synchronized: hace falta el cerrojo de B. this es este mismo FicheroA, que se le pasa a B
  • Si B está ocupado, el hilo espera, pero sigue teniendo el cerrojo de A

Esto es «retener y esperar»: tiene A y pide B.

FicheroB: lo mismo al revés

  • metodoB(FicheroA a) es igual que metodoA, pero entra en B y después pide A con a.metodoA(this)
  • También es synchronized: coge el cerrojo de B

Uno entra por A y pide B. El otro entra por B y pide A.

Los hilos: cada uno por su lado

    @Override
    public void run() {
        a.metodoA(b);
    }
  • Hilo1 llama a a.metodoA(b): empieza por el fichero A
  • Hilo2 llama a b.metodoB(a): empieza por el fichero B
  • Reciben los dos ficheros por el constructor: son los mismos dos objetos para los dos hilos

Principal: arranca los dos hilos

    public static void main(String[] args) throws InterruptedException {
        FicheroA a = new FicheroA();
        FicheroB b = new FicheroB();

        Thread h1 = new Thread(new Hilo1(a, b), "Hilo 1");
        Thread h2 = new Thread(new Hilo2(a, b), "Hilo 2");
        h1.start();
        h2.start();

        Thread.sleep(3000);
        System.out.println(h1.getName() + ": " + h1.getState());
        System.out.println(h2.getName() + ": " + h2.getState());
    }
  • Se crean un solo FicheroA y un solo FicheroB y se arrancan los dos hilos
  • Después de 3 segundos, main pregunta el estado de cada hilo con getState()

La película, paso a paso

  1. Segundo 0. El hilo 1 entra en A: coge el cerrojo de A. El hilo 2 entra en B: coge el cerrojo de B
  2. Los dos duermen un segundo, sin soltar su cerrojo
  3. Segundo 1. El hilo 1 pide el cerrojo de B: lo tiene el hilo 2, espera
  4. El hilo 2 pide el cerrojo de A: lo tiene el hilo 1, espera
  5. Para siempre: el hilo 1 espera al 2 y el hilo 2 espera al 1

Qué sale en pantalla

Hilo 1 entra en fichero_A
Hilo 2 entra en fichero_B
Hilo 1 intentando acceder a fichero_B
Hilo 2 intentando entrar en fichero_A
Hilo 1: BLOCKED
Hilo 2: BLOCKED
▮ (el programa no termina)
  • No hay ningún error: el programa simplemente se queda parado
  • El orden de las dos primeras líneas puede cambiar. Lo que no cambia es el final
  • En NetBeans, el botón de ejecución sigue activo: hay que detenerlo a mano

Los estados de un hilo

EstadoCuándo ocurre
NEWSe ha creado con new Thread(...), pero aún no se ha llamado a start()
RUNNABLEEstá en marcha (o listo para que le toque)
BLOCKEDEspera el cerrojo de un objeto synchronized
WAITINGEspera un aviso: wait() o join()
TIMED_WAITINGEspera un tiempo: sleep()
TERMINATEDHa acabado su run()

Cómo reconocer el interbloqueo

  • El programa no termina y no escribe nada más
  • Con getState(), los hilos implicados salen en BLOCKED
  • No es lo mismo que un hilo dormido: con sleep() el estado es TIMED_WAITING y despierta solo

Con wait() sin notify(), los hilos se quedan colgados en WAITING. Con interbloqueo, en BLOCKED. Los dos «cuelgan», pero por motivos distintos.

Cómo evitarlo: el mismo orden

El interbloqueo necesita una espera en círculo. Si todos piden los recursos en el mismo orden, no puede haber círculo.

  • Hilo 1: primero A, después B
  • Hilo 2: primero A, después B (antes: primero B y después A)
  • El que llega segundo se queda esperando A y no retiene nada: cuando el primero termina, entra

Proyecto InterbloqueoResuelto

Solución: un trabajo que pide dos ficheros

    public void run() {
        String nombre = Thread.currentThread().getName();
        synchronized (primero) {
            System.out.println(nombre + " tiene " + primero.getNombre());
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
            }
            synchronized (segundo) {
                System.out.println(nombre + " tiene " + primero.getNombre() + " y " + segundo.getNombre() + ": trabaja");
            }
        }
        System.out.println(nombre + " termina");
  • synchronized (primero) { … }: coge el cerrojo de ese objeto mientras dura el bloque
  • Dentro, otro synchronized (segundo) { … }: el segundo fichero
  • Trabaja con los dos y, al cerrar las llaves, suelta los dos cerrojos

Lo que cambia: el orden de los argumentos

    public static void main(String[] args) {
        Fichero a = new Fichero("A");
        Fichero b = new Fichero("B");

        new Thread(new Trabajo(a, b), "Hilo 1").start();
        new Thread(new Trabajo(a, b), "Hilo 2").start();
    }
  • Los dos hilos reciben (a, b): primero A y después B
  • Si el hilo 2 recibiera (b, a), volvería el interbloqueo. Solo cambia el orden

Otras formas de evitarlo

  • Menos cerrojos: si un solo objeto protege los dos ficheros, no hay nada que esperar en círculo
  • No retener: soltar lo que se tiene antes de pedir otra cosa
  • No esperar para siempre: pedir el recurso con un tiempo máximo y rendirse si no llega (en Java, con la clase ReentrantLock; no la vemos aquí)
  • Pensarlo antes: dibujar quién pide qué y en qué orden

Errores típicos

  • Pensar que sleep() suelta el cerrojo: no lo suelta, solo wait() lo hace
  • Que cada hilo pida los recursos en orden distinto
  • Creer que un programa parado es siempre un interbloqueo: también se queda parado si falta un notify()
  • Probarlo una vez, que salga bien, y darlo por bueno: el interbloqueo depende del momento
  • Llamar a wait() con un cerrojo y quedarse con otro: el otro no se suelta
