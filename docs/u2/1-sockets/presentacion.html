Una idea para recordarlo: el bar

¿Cómo se encuentran? Dirección IP y puerto

Una dirección completa tiene dos partes, como la de una casa:

  • Dirección IP: el edificio. Dice a qué ordenador vamos. Ejemplo: 192.168.1.200
  • Puerto: el piso. Dice a qué programa de ese ordenador hablamos. Es un número.

En un mismo ordenador puede haber varios servidores a la vez, cada uno en su puerto: la web en el 80, el correo en otro...

Los puertos, por rangos

RangoPara qué
0 – 1023Servicios conocidos (web 80, FTP 21, SSH 22)
1024 – 49151Los podemos usar en nuestras aplicaciones
49152 – 65535Temporales: los usa el sistema

Nuestros servidores usarán puertos entre 1024 y 49151. Por ejemplo, el 2000.

La mochila de redes: las importaciones

Antes de escribir un programa de red hay que traer las clases que vamos a usar. Se hace con import, al principio del archivo.

Hay dos formas de hacerlo. Las dos funcionan igual. Pero una es más limpia.

Dos formas de importar

Con asterisco (rápida)


import java.net.*;
import java.io.*;

Una por una (limpia)


import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.PrintWriter;
import java.net.ServerSocket;
import java.net.Socket;

¿Por qué es mejor la de la derecha?

  • El * trae todas las clases del paquete, aunque solo uses dos. La otra trae solo las que usas.
  • Leyendo los import ya sabes qué usa el programa, sin leer el código.
  • Evita confusiones cuando dos paquetes tienen una clase con el mismo nombre.
  • Es la forma que se usa en proyectos profesionales.

Regla de clase: importaremos siempre una clase por línea. Si escribes los import en NetBeans, te los sugiere solo.

Qué es cada cosa de la mochila

El primer contacto: sin conexión no hay química

Para que dos programas se hablen, primero tiene que haber una conexión.

  • El servidor abre un puerto y espera.
  • El cliente llama a ese puerto.
  • Cuando se encuentran, queda un canal entre los dos.

Orden importante: el servidor se arranca siempre primero. Si el cliente llama y nadie escucha, da error.

Lo nuevo de hoy

Clase

ServerSocket: la usa el servidor. Se crea con el número de puerto y se queda escuchando en él.

Método

accept() de la clase ServerSocket: es un método bloqueante: detiene el programa hasta que un cliente se conecta. Cuando llega, devuelve un Socket.

Clase

Socket: el canal de comunicación con el otro programa. El cliente lo crea con el nombre del ordenador y el puerto del servidor.

El servidor, línea por línea

        ServerSocket ss = new ServerSocket(12349);
        System.out.println("Esperando conexión...");
        Socket s = ss.accept();
        System.out.println("Conectado");
  1. Crea un ServerSocket en el puerto 12349. Desde aquí el puerto está abierto.
  2. Escribe que está esperando. Todavía no ha llegado nadie.
  3. El método accept() de la clase ServerSocket es bloqueante: para el programa aquí. No pasa a la línea siguiente hasta que un cliente llame.
  4. Ya hay cliente: accept() devolvió el Socket s y se escribe «Conectado».

El cliente, línea por línea

        Socket s = new Socket("localhost", 12349);
        System.out.println("Conectado");
  1. Crea un Socket con dos datos: "localhost" (el ordenador del servidor; aquí, el mismo en el que estamos) y 12349 (el puerto donde escucha).
  2. Si la conexión sale bien, escribe «Conectado».

Los dos números de puerto deben ser el mismo. Si no, el cliente llama a una puerta donde no vive nadie.

¿Y si ejecutas el Cliente sin arrancar el servidor? Java lanza ConnectException: Connection refused (conexión rechazada): nadie escuchaba.

Si el puerto sigue ocupado

Si ejecutas el Servidor dos veces, la segunda falla con BindException: Address already in use: el puerto lo tiene todavía la primera ejecución.

Lo normal es parar el programa con el cuadrado rojo de la ventana Output de NetBeans. Si no basta, ciérralo desde Windows:

  1. Abre el Símbolo del sistema (cmd).
  2. Busca quién usa el puerto: netstat -ano | findstr 12349. El número de la última columna es el PID.
  3. Ciérralo: taskkill /PID número /F, cambiando número por ese PID.

Si netstat no muestra nada, el puerto ya está libre.

Hablar y escuchar: los dos canales

Con el Socket ya tenemos la conexión. Pero para conversar hacen falta dos canales:

  • Uno para escuchar lo que dice el otro (entrada)
  • Uno para hablar (salida)

Como un teléfono: tiene auricular para escuchar y micrófono para hablar. Cliente y servidor crean los mismos dos canales, con el mismo código.

Lo nuevo de hoy

Método

getInputStream() de la clase Socket: da la entrada del socket, por donde llegan los bytes que envía el otro.

Método

getOutputStream() de la clase Socket: da la salida del socket, por donde se envían los bytes al otro.

Clase

InputStreamReader: convierte los bytes que llegan en caracteres.

Clase

BufferedReader: lee texto línea a línea con su método readLine(). Es el canal para escuchar.

Clase

PrintWriter: escribe texto con println(), como System.out, pero hacia el otro programa. Es el canal para hablar.

El canal para escuchar

        Socket s = ss.accept();
        BufferedReader br = new BufferedReader(new InputStreamReader(s.getInputStream()));
        PrintWriter pw = new PrintWriter(s.getOutputStream(), true);
  1. s.getInputStream(): la entrada del socket. Por aquí llegan bytes.
  2. new InputStreamReader(...): convierte esos bytes en caracteres.
  3. new BufferedReader(...): junta los caracteres y deja leer una línea entera cada vez. Lo guardamos en br.

Va por capas, de dentro hacia fuera: bytes → caracteres → líneas.

El canal para hablar

        Socket s = ss.accept();
        BufferedReader br = new BufferedReader(new InputStreamReader(s.getInputStream()));
        PrintWriter pw = new PrintWriter(s.getOutputStream(), true);
  1. s.getOutputStream(): la salida del socket. Por aquí se envían los datos.
  2. new PrintWriter(..., true): permite escribir texto con println(). Lo guardamos en pw.
  3. El true es el autoFlush: cada println() se envía en el momento. Sin él, el texto podría quedarse esperando en el buzón y el otro no recibirlo.

Servidor y cliente: el mismo código

Servidor

        BufferedReader br = new BufferedReader(new InputStreamReader(s.getInputStream()));
        PrintWriter pw = new PrintWriter(s.getOutputStream(), true);

Cliente

        BufferedReader br = new BufferedReader(new InputStreamReader(s.getInputStream()));
        PrintWriter pw = new PrintWriter(s.getOutputStream(), true);

Las dos líneas son idénticas. Lo que cambia es cómo consiguen el Socket: el servidor con accept() y el cliente con new Socket(...).

Plantilla: este proyecto, Canales, es el punto de partida de los siguientes. Servidor y cliente conectan y preparan br y pw. Desde aquí solo añadimos lo que cada ejercicio pide: println() para hablar y readLine() para escuchar.

Siempre flush positivo

Cuando haces println() en un PrintWriter, el texto no sale siempre al momento.

Java lo guarda en una zona de espera, el buffer, y lo envía cuando le parece. Es como un buzón: metes la carta, pero no se va hasta que pasa el cartero.

Con flush («vaciar») obligamos a que el buzón se vacíe y la carta salga ya.

Lo nuevo de hoy

Concepto

Buffer: zona de espera donde Java guarda el texto antes de enviarlo. Mejora la velocidad, pero retrasa el envío.

Concepto

Flush: vaciar el buffer y enviar ya todo lo que haya esperando.

Parámetro

true como segundo dato de new PrintWriter(salida, true): es el autoFlush. Hace flush solo, cada vez que se usa println().

Animación: sin autoFlush y con autoFlush

Servidor
pw.println("Hola")
📭 Sin true: «Hola» espera en el buffer
Hola
💻
Cliente
Esperando... (readLine() bloqueado)
El servidor dice: Hola

Con true (autoFlush): el texto sale en el momento y el cliente lo recibe.

El servidor con autoFlush

        PrintWriter pw = new PrintWriter(s.getOutputStream(), true);
        pw.println("Hola, cliente");
  1. El true activa el autoFlush del PrintWriter.
  2. Este println() envía el saludo en ese instante.

El cliente espera el saludo

        BufferedReader br = new BufferedReader(new InputStreamReader(s.getInputStream()));
        String linea = br.readLine();
        System.out.println("El servidor dice: " + linea);
  1. El método readLine() de la clase BufferedReader también es bloqueante: espera hasta que llega una línea entera.
  2. Cuando llega, la muestra. Salida: El servidor dice: Hola, cliente

¿Y si se nos olvida el true?

PrintWriter pw = new PrintWriter(s.getOutputStream());
  • El saludo se queda en el buffer y no sale.
  • El cliente se queda esperando en readLine(). Si el servidor termina antes de enviarlo, el cliente recibe null y el saludo se pierde.
  • No da ningún error: el programa simplemente no funciona.

Regla de clase: en un PrintWriter sobre un socket, siempre true. Flush positivo, nunca negativo.

Ejercicio 1: ¿dónde está mi saludo?

Abre el proyecto Flush. Vamos a estropearlo y a arreglarlo.

  1. Ejecuta Servidor y después Cliente. Sale «El servidor dice: Hola, cliente».
  2. En Servidor, quita el true del PrintWriter y ejecuta otra vez. ¿Qué muestra el cliente?
  3. Añade Thread.sleep(30000); al final del main (con throws Exception) y ejecuta. ¿Qué hace el cliente ahora?
  4. Arréglalo de dos formas: con el true y con pw.flush(); después del println.

Apunta qué ves en cada paso y por qué.

Qué ha pasado

  • Sin el true, el saludo se queda en el buffer.
  • Si el servidor termina enseguida, el socket se cierra y el saludo se pierde: el cliente muestra null.
  • Si el servidor sigue vivo (sleep), el saludo sigue sin salir y el cliente se queda esperando en readLine().
  • Con true o con flush(), el saludo sale en el momento.

Dos síntomas, una sola causa: el texto no salió del buffer.

El salto de línea nos guiará

Por la red los datos viajan seguidos, como una cinta sin cortes. ¿Cómo sabe el cliente dónde acaba un mensaje y empieza el siguiente?

Con un salto de línea. Cada mensaje es una línea: termina cuando llega el salto.

Hola⏎¿Qué tal?⏎

Lo nuevo de hoy

Método

println() de la clase PrintWriter: escribe el texto y añade el salto de línea al final. Ese salto marca el fin del mensaje.

Método

readLine() de la clase BufferedReader: lee hasta el salto de línea y devuelve esa línea como String, sin el salto. Si todavía no ha llegado el salto, espera.

Valor

null: lo que devuelve readLine() cuando el otro programa ha cerrado la conexión y ya no hay más líneas.

Hola⏎
💻

readLine() → «Hola»
readLine() → «¿Qué tal?»

Cada println() del servidor se recibe con un readLine() del cliente.

El servidor envía dos mensajes

        pw.println("Hola");
        pw.println("¿Qué tal?");
  1. Primer mensaje: Hola y su salto de línea.
  2. Segundo mensaje: ¿Qué tal? y su salto de línea.

Con el autoFlush (true) de antes, cada línea sale en el momento.

El cliente los recibe, línea por línea

        String linea;
        linea = br.readLine();
        System.out.println("Recibido: " + linea);
        linea = br.readLine();
        System.out.println("Recibido: " + linea);
  1. Declara la variable linea, de tipo String, donde guardará lo que lea.
  2. br.readLine() espera hasta que llega la primera línea y la guarda en linea. Se muestra «Recibido: Hola».
  3. Segundo readLine(): recibe «¿Qué tal?».

Cuidado con el salto de línea

  • Un println() por mensaje y un readLine() para leerlo. Si el cliente pide más líneas de las que envía el servidor, se queda esperando.
  • Si un mensaje no lleva salto de línea (por ejemplo, con print() en vez de println()), readLine() no sabe dónde acaba y sigue esperando.
  • Un mensaje no debe llevar saltos de línea dentro: se leería como dos mensajes.

Regla de clase: un mensaje = una línea. El salto de línea nos guía.

Ejercicio 2: pares e impares por la red

Vamos a hacer dos programas:

  • Cliente: genera 25 números aleatorios entre 0 y 100 y se los envía al servidor.
  • Servidor: recibe cada número y le contesta si es par o impar.
  • El cliente muestra el resultado:
27 – impar
13 – impar
72 – par
…

Antes de programar: el plan

Cada número es un mensaje de una línea. Piénsalo como una conversación:

  1. El cliente envía un número.
  2. El servidor lo lee y contesta «par» o «impar».
  3. El cliente lee la respuesta y la muestra.
  4. Se repite 25 veces.

¿Cómo sabe el servidor que debe dejar de leer? Cuando el cliente termina y cierra la conexión, readLine() devuelve null.

Solución: el servidor

        ServerSocket ss = new ServerSocket(12349);
        System.out.println("Esperando conexión...");
        Socket s = ss.accept();
        BufferedReader br = new BufferedReader(new InputStreamReader(s.getInputStream()));
        PrintWriter pw = new PrintWriter(s.getOutputStream(), true);
        String linea;
        while ((linea = br.readLine()) != null) {
            int n = Integer.parseInt(linea);
            pw.println(n % 2 == 0 ? "par" : "impar");
        }
        System.out.println("Cliente desconectado");
  1. Abre el puerto y espera al cliente.
  2. Crea los dos canales.
  3. Declara linea.
  4. El while lee una línea y sigue mientras no sea null.
  5. Convierte la línea en número con Integer.parseInt y contesta «par» o «impar» según el resto de dividir entre 2.
  6. Cuando el cliente se desconecta, sale del bucle y avisa.

Solución: el cliente

        Socket s = new Socket("localhost", 12349);
        BufferedReader br = new BufferedReader(new InputStreamReader(s.getInputStream()));
        PrintWriter pw = new PrintWriter(s.getOutputStream(), true);
        for (int i = 0; i < 25; i++) {
            int n = (int) (Math.random() * 101);
            pw.println(n);
            String linea = br.readLine();
            System.out.println(n + " – " + linea);
        }
  1. Se conecta al servidor y crea los canales.
  2. for de 25 vueltas.
  3. Número aleatorio entre 0 y 100.
  4. Lo envía.
  5. Lee la respuesta y la muestra junto al número.

Siempre uno tiene que dar el brazo a torcer

Una conversación necesita turnos: uno habla y el otro escucha.

Pero readLine() es bloqueante. ¿Qué pasa si los dos empiezan escuchando?

Los dos esperan a que el otro hable. Y como los dos esperan, nadie habla nunca.

Animación: los dos esperan

El código que se queda bloqueado

Servidor

        String linea;
        linea = br.readLine();
        System.out.println("El cliente dice: " + linea);
        pw.println("Hola, cliente");

Cliente

        String linea;
        linea = br.readLine();
        System.out.println("El Servidor dice: " + linea);
        pw.println("Hola");

Los dos empiezan por readLine(). Es como dos personas al teléfono, cada una esperando a que la otra diga «¿Hola?».

La solución: uno habla primero

Hay que decidir quién habla primero. Ese «da el brazo a torcer». El otro escucha.

  1. El que habla primero hace println() y después readLine().
  2. El que escucha primero hace readLine() y después println().

En nuestro ejemplo habla primero el cliente (pw.println("Hola")) y el servidor escucha. Es el orden del proyecto Dialogo.

El protocolo: un guion con turnos

Al orden de los mensajes que se acuerdan cliente y servidor se le llama protocolo. Es un guion:

TurnoClienteServidor
1habla: println()escucha: readLine()
2escucha: readLine()habla: println()

Cada println() de uno tiene que encontrarse con un readLine() del otro. Si los guiones no encajan, el programa se bloquea. Es la misma idea del interbloqueo de la unidad 1: cada uno espera algo que solo el otro puede dar.

Si te vas, cierra

Cuando sales de una habitación, apagas la luz y cierras la puerta.

Con la red pasa igual: cuando terminamos, hay que cerrar lo que hemos abierto. El puerto, la conexión y los canales usan recursos del ordenador.

Si no se cierran, quedan ocupados. En un servidor que sigue funcionando mucho tiempo, se acaban acumulando.

Lo nuevo de hoy

Método

close(): cierra y libera el recurso. Lo tienen las clases BufferedReader, PrintWriter, Socket y ServerSocket.

Concepto

Orden de cierre: al revés de como se abrió. Primero los canales (br y pw), luego el Socket y por último el ServerSocket.

Concepto

Cuando un programa cierra su Socket, al otro le avisa: su readLine() devuelve null.

Abrir y cerrar: orden inverso

Se abre asíSe cierra así
1. ServerSocket ss4. ss.close()
2. Socket s3. s.close()
3. BufferedReader br y PrintWriter pw1-2. br.close() y pw.close()

Como ponerse y quitarse la ropa: lo último que te pones es lo primero que te quitas.

El servidor cierra todo

        br.close();
        pw.close();
        s.close();
        ss.close();
  1. Cierra los dos canales: br y pw.
  2. Cierra el Socket de la conexión con el cliente.
  3. Cierra el ServerSocket: libera el puerto 12349. Solo lo tiene el servidor.

El cliente cierra todo

        br.close();
        pw.close();
        s.close();
  1. Cierra sus dos canales.
  2. Cierra su Socket. El cliente no tiene ServerSocket, así que una línea menos.

Al cerrar el cliente, el readLine() del servidor devuelve null. Así el servidor sabe que el cliente se ha ido.

Lee con moderación

Para conversar mucho rato, el servidor repite en un bucle: lee un mensaje, contesta, y vuelve a leer.

La regla: un readLine() por vuelta. Lo que lees, lo guardas en una variable y usas la variable. No vuelvas a llamar a readLine().

Cada readLine() se come una línea. Si llamas dos veces, la primera se pierde y la segunda se queda esperando.

El bucle correcto

        String linea;
        while ((linea = br.readLine()) != null) {
            System.out.println("El cliente dice: " + linea);
            pw.println("Hola");
        }
  1. El while hace tres cosas a la vez: lee con readLine(), guarda la línea en linea y comprueba que no sea null. Sigue mientras lleguen mensajes.
  2. Muestra el mensaje usando la variable linea.
  3. Contesta «Hola». Después vuelve arriba a leer el mensaje siguiente.

El bucle acaba cuando el cliente se desconecta: readLine() devuelve null (recuerda el 7º paso: cerrar avisa al otro).

El bucle incorrecto ❌

        String linea;
        while ((linea = br.readLine()) != null) {
            System.out.println("El cliente dice: " + br.readLine());
            pw.println("Hola");
        }
  • El while ya lee el mensaje 1 y lo guarda en linea.
  • Dentro, el readLine() otra vez se queda esperando el mensaje 2.
  • Pero el cliente no enviará el 2 hasta recibir la respuesta al 1. Los dos esperan: bloqueo, como en el 6º paso.

Y aunque no se bloqueara, el mensaje que se muestra sería otro distinto del que se guardó en linea.

Pruébalo: la conversación completa

  1. Ejecuta Servidor del proyecto LeeConModeracion y después Cliente.
  2. El cliente envía Mensaje 1, Mensaje 2 y Mensaje 3, y muestra tres veces «El Servidor dice: Hola».
  3. El servidor muestra los tres mensajes y, al irse el cliente, «Cliente desconectado».
  4. Ahora cambia a ServidorMal y mira qué pasa.

A veces, hay que saber callarse

El servidor sabe que el cliente ha terminado cuando readLine() devuelve null.

Pero, ¿y si el cliente quiere decir «ya no tengo más que decir» y aun así seguir escuchando las respuestas?

Con close() no se puede: cierra la conexión entera y el cliente deja de oír. Necesita cerrar solo la parte de hablar.

Lo nuevo de hoy

Método

shutdownOutput() de la clase Socket: cierra solo la salida. El otro programa recibe null en su readLine(), como si te hubieras ido, pero tú sigues pudiendo escuchar.

Comparación

close() de la clase Socket: cierra todo, hablar y escuchar.

        for (int i = 1; i <= 3; i++) {
            pw.println("Mensaje " + i);
        }
        s.shutdownOutput();
        String linea;
        while ((linea = br.readLine()) != null) {
            System.out.println("El Servidor dice: " + linea);
        }
  1. Envía tres mensajes con un for.
  2. s.shutdownOutput(): «ya no hablo más». El servidor lo nota porque su readLine() devuelve null.
  3. Sigue leyendo con un while hasta que el servidor, al acabar, cierre la conexión.

Con close() no funciona ❌

        for (int i = 1; i <= 3; i++) {
            pw.println("Mensaje " + i);
        }
        s.close();
  • s.close() cierra todo: también la parte de escuchar.
  • Al llamar después a readLine(), Java lanza SocketException: Socket closed.
  • Las respuestas del servidor se pierden.

Resumen: shutdownOutput() = «me callo, pero te sigo oyendo». close() = «me voy».

El servidor del ejemplo

        String linea;
        while ((linea = br.readLine()) != null) {
            System.out.println("El cliente dice: " + linea);
            pw.println("Recibido: " + linea);
        }
        System.out.println("El cliente ya no habla");
        br.close();
        pw.close();
        s.close();
        ss.close();
  1. Contesta a cada mensaje con el bucle de siempre.
  2. Cuando el cliente se calla, readLine() devuelve null y el servidor avisa.
  3. Cierra todo: eso hace que el cliente, que seguía escuchando, también reciba null y termine.
